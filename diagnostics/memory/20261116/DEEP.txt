Units and accounting
  MiB = 1,048,576 bytes. Private resident pages, private commit and requested
  live allocation sizes are different measurements. A heap page may contain
  several allocation owners and allocator bookkeeping/free space. Do not add
  the allocation table below to a working-set table, or subtract process totals
  from different runs as a controlled savings measurement.

Snapshot buffer
  buffer 2,097,152 bytes; actual filled samples approximately 1.66-1.69 MB;
  530-558 rows, capacity 1024 at 288 bytes/row. Most of the 2 MiB is needed.
  An adaptive floor would save only a few hundred KiB on this machine.
  In-buffer Windows string pointers prohibit moving a completed native buffer.

GC owner, and reduction
  A matching CoreCLR diagnostic host exposed the retained object types:
  DiskInfoToolkit.PCI kept 2523 vendors, 21074 devices, 17860 subdevices and
  tens of thousands of strings/list nodes for its entire embedded pci.ids.gz.
  Even closing LHM left most of the catalog rooted. This is a catalog for name
  lookup, not current sensor samples or historical temperature readings.
  CoreCLR GC sizes are diagnostic evidence, not NativeAOT memory totals.

  A streaming lookup now reads only the requested vendor/device from the same
  compressed resource with the same parser. It does not skip controller names.
  141 distributed lookup cases compare found/not-found, vendor and device names
  against the original 2.2.2 NuGet assembly. All device/sensor identities matched.

  The reduction was independently verified in the NativeAOT service:
  old aggressive-GC sample: heap 6,953,240; committed 6,971,392 bytes;
  streaming sample:        heap   641,800; committed   659,456 bytes.
  Temporary GC instrumentation overhead exists in both observations.
  The streaming run retained all 15 actual temperature readings and CPU watts.

Signature projection reduction
  Core commit 38f49ff uses existing amethystate Store point get/set under the
  same signatures/verdicts/path layout. It does not construct the whole resident
  ReactiveMap. The disk layout, file stamp/resolver checks, write debounce
  and shutdown save_now remain. The current image worker is already a hot cache.
  Tests write using the legacy map, read/update via point access, reopen through
  the legacy map and verify Unicode/dotted keys, unrelated entries, stale/missing
  records, malformed-record fallback and flushed updates. No data-file migration
  or new Rust dependency is needed.

Kept intentionally
  Existing process-event retention and VM working-set estimation semantics.
  The event payload budget is approximate; Arc/string sharing, VecDeque capacity
  and structure overhead make it distinct from a strict physical 4 MiB limit.
  QueryWorkingSet scratch is transient and dropped after a probe. Reusing it
  would reduce churn but retain the large allocation, not save steady RAM.
  Periodic HeapOptimizeResources is not shipped: in these trials it returned
  only roughly 1.1-1.3 MiB of private commit, and active allocations cannot be
  freed by heap purging. Working-set trimming is not used to mask ownership.

Signature cache TTL requested by the user on 2026-11-16:
  Entries expire 24 hours after saved_at_ms; reads do not renew the age.
  Hot verdicts carry the original disk timestamp and cannot bypass expiry.
  Expired lookups delete the entry; the existing image worker also cleans at
  startup and hourly, including while requests keep arriving. Disk writes
  retain the existing five-second debounce and shutdown flush behavior.
  Missing old timestamps are expired. Future timestamps miss without unsigned
  subtraction and are not mass-deleted as old. Decode errors are not TTL.
  Cleanup uses a temporary list of keys and point reads, never a resident
  ReactiveMap of all values. Only direct entries under the correct StorePath
  prefix are removed; deep children and neighboring prefixes are preserved.
